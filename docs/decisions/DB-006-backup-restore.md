# ADR: DB-006 备份恢复基线

日期：2026-09-22
状态：已实现并测试通过；磁盘满未做故障注入

`packages/storage/src/backup.ts` 提供一致备份、备份校验与恢复；`packages/storage/src/runtimeDatabase.ts` 把运行参数、迁移前备份与迁移串成唯一启动入口。

## 决策

1. **备份只能用 SQLite 在线备份 API，不能复制文件。** WAL 下最新已提交的页在 `pm.db-wal` 里，单独复制 `pm.db` 会得到一个缺数据或打不开的文件——`DATABASE_PLAN.md` 第 9 节已写明这一点，这里把它变成实现约束。
2. **备份产物必须转出 WAL，成为自包含单文件。** 这是实测发现的：在线备份会连同源库头部一起复制，目标是 WAL 模式，因此它刚写入的页可能落在目标的 `-wal` 伴生文件里。只把主文件 rename 走，等于把备份的完整性留在一个被丢弃的临时文件里。发布前对目标执行 `journal_mode = DELETE`（该操作会把 WAL 折叠回主文件并删除伴生文件），再删掉可能残留的 `-wal`/`-shm`。
3. **先写临时名，验证通过后才原子改名。** 备份写到 `<backups>/.tmp/<uuid>.part`，随后打开（只读）跑 `integrity_check` 并统计实体数；未通过校验的备份被**删除**，不留下一个看起来可用的文件。发布名形如 `pm-20260922T010000000Z-pre-migration-a1b2c3d4.db`，时间戳可排序，短随机后缀避免同毫秒覆盖。
4. **校验读取只读连接，且必须触碰 schema。** 损坏的文件在 `new Database()` 时不会报错，只有真正读页才失败，所以校验要查 `sqlite_master` 与 `integrity_check`，而不是只看能不能打开。损坏检测实测覆盖"擦掉文件头 16 字节"与"截断到 2048 字节"两种。
5. **恢复前先删除目标库的旧 `-wal` 与 `-shm`。** 它们属于被替换的那个库；留着会让刚恢复的文件被读成损坏。复制同样走临时名 + 原子 rename，失败的恢复不会在目标位置留下半个数据库。
6. **恢复后重新校验，并把结果返回给调用方。** DB-006 的验收是"恢复副本通过 `integrity_check` 且实体数一致"，所以返回的是校验结果本身，而不是一句"成功"。
7. **启动顺序固定为：校验目录 → 打开并读参数 → 读迁移计划 → 迁移前备份 → 迁移。** `openRuntimeDatabase` 是唯一入口。先读计划再写任何东西，数据库版本高于应用时直接抛 `MIGRATION_VERSION_REGRESSION`，由调用方转入只读诊断（`inspectRuntimeDatabase` 只读不建库、不迁移）。只在"库已有 schema 且有待执行迁移"时备份——空库没有可备份的内容。
8. **失败不泄漏句柄。** 启动路径上任何一步抛错都会先关闭连接再抛，否则调用方转诊断时会撞上写锁。
9. **保留策略默认保留 5 份。** `pruneDatabaseBackups` 只删除已发布的 `.db`，从不遍历 `.tmp`。

## 实测证据

`pnpm exec vitest run --config vitest.backend.config.mjs packages/storage/src/backup.test.ts packages/storage/src/runtimeDatabase.test.ts`，17 个用例通过：

- 发布：哈希 64 位十六进制、`schemaVersion=1`、`entityCounts.projects=3`、文件存在、`.tmp` 为空。
- 一致性：备份后再写入 3 行，第一份备份仍是 2 行，第二份是 5 行（备份取的是备份时刻的已提交快照）。
- **并发**：另一连接持 `BEGIN IMMEDIATE` 且已写入未提交行时备份成功，且结果不含该行；回滚后计数不变。
- 损坏：文件头被擦、文件被截断两种情况下 `verifyDatabaseBackup` 都返回 `ok: false` 且带 `problem`，不抛异常。
- 恢复：恢复到新路径后实体数一致，并且**恢复出来的库仍可继续写入**（再插一行成功）。
- 恢复覆盖：目标位置原有的 `-wal`/`-shm` 在恢复后不存在。
- 拒绝：损坏的备份不允许用于恢复（`BACKUP_VERIFY_FAILED`）。
- 保留：4 份备份按新到旧列出，`keep=2` 时删掉最旧的两份，`.tmp` 目录保留。
- 名称：label 中的路径分隔符与 `..` 被清理，`pre-migration ../etc` 产出 `...-pre-migration.etc-<hex>.db`。
- 启动入口：空目录建立全部目录与 `0001` schema；第二次启动不迁移也不备份；有待执行迁移时先生成 `pre-migration` 备份（该备份里**没有**新表，证明它取自迁移前）；库版本高于应用时拒绝启动且诊断报告 `read-only`；对没有库文件的目录做诊断不会创建库；关闭时 WAL 被折叠为 0 字节；用启动备份覆盖已迁移的库后，重新打开回到版本 1、新表不存在、原数据仍在。

## 未验证项与边界

- **磁盘满未做故障注入。** 备份失败会删除临时文件并报 `BACKUP_FAILED`，但没有实测。
- **保留策略未接入自动清理时机。** 目前只在启动备份后调用一次；长期运行下的定期清理属于 DB-016/BE-036。
- **启动入口尚未接入 daemon。** `pnpm runtime:dev` 不会打开数据库，页面也没有新增可联调接口。BE-009 起的 repository/service 直接调用 `openRuntimeDatabase`；把句柄接进 daemon 路由的那一步属于第一个需要它的 API 任务（BE-013）。
- **备份未加密。** 与 `Q-DB-005` 一致，依赖 OS 用户权限；备份文件是数据库的完整副本，含全部业务数据。
- **跨卷备份未验证。** 备份目录与数据库目录在同一卷时 rename 必定原子；计划中的布局满足这一点，但没有对跨卷情形做检测或降级。
